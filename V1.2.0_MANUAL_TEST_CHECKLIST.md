## Worth paying attention to

1. **First-time transport is HTTP.** HTTPS is recommended once a certificate exists and is never
   switched on or off for you. Confirm the wording makes the difference clear.
2. **Routing to a display that is showing a Multiview** now just happens, from the A/V Matrix, the
   Multiview page's display drop and both kinds of User. A route that fails puts the Multiview back.
3. **A source whose Session 2 has no multicast address** is *Configuration required* for Multiview and a
   perfectly good source for an ordinary route.
4. **The certificate has to match the address.** Switching adapters leaves a generated certificate naming
   the old one, and OmniSuite refuses to start HTTPS rather than serving one no browser will accept.
5. **Duplicate friendly names** are told apart by the device's own Location. Set Location on a couple of
   units and rescan to see it.
6. **USB and Multiview as a restricted User.** Read-only state is verified by tests; an actual pair or
   unpair from a User account should only be tried where it is safe to re-cable.
7. **The restricted screen on a real phone.** Checked at 390 px in a headless browser; a real handset is
   the honest test.
8. **Long runs.** Two observations are open and not explained: route latency that seemed to rise with how
   long OmniSuite had run, and memory growth of roughly 2.5 MB an hour. If you can leave OmniSuite running
   for days, note the route time at the start and the end, and Task Manager's memory for the process. The
   opt-in timing record (`OMNI_ROUTE_DIAG=1` in the environment OmniSuite starts with) writes
   `route_diag.jsonl` to the data folder.
