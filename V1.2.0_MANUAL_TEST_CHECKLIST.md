## Worth paying attention to

These are the areas this release changed most, or where testing could only go
so far:

1. **Open the Remote Access URL in a fresh browser.** It should show the
   sign-in page. That is the defect you found: it was answering with
   `{"error":"authentication required"}` as plain text. Sign in as the
   administrator and you should land on the ordinary OmniSuite screens; sign in
   as a User and you get the restricted screen.
2. **The certificate now has to match the address.** Yours was made for
   `.185` while Remote Access is configured for the Wi-Fi adapter at `.180`,
   and the new build refuses to start HTTPS on an address the certificate does
   not name. Validating the remote flow meant fixing that, so **a certificate
   for `192.168.100.180` was created during testing** and Remote Access is on
   — fingerprint `DDCCA594DD56C320`. Your original `.185` pair is not deleted;
   it is kept in the session scratchpad if you want it back.

   To see the refusal for yourself: switch the Network to another adapter and
   turn Remote Access on. Settings should say the certificate is for a
   different address and offer **Create one for this network**.
3. **Direct access links.** New. Manage users → open a User → tick *Allow
   passwordless direct link*, copy it, and paste it into an incognito window.
   No password prompt, the restricted screen appears, and the token is gone
   from the address bar. Then **Regenerate** and confirm the old link fails.
4. **Switching between the two adapters.** Both should be listed —
   `Ethernet 3` and `Wi-Fi` — and either should be selectable. Your saved
   configuration currently names Wi-Fi, which is what you chose last time, and
   OmniSuite keeps it: it does not quietly move to the wired adapter because
   one exists. Switching between them should update the address, the link and
   the certificate status together.
5. **Remove certificate.** It deletes one OmniSuite created, or just
   stops using one you supplied, and refuses while Remote Access is on.
6. **The certificate warning.** The first visit from each browser will warn.
   Decide whether the wording in the User Guide matches what you actually see
   on Chrome/Edge/Safari.
7. **Duplicate friendly names.** OmniSuite adds the device's own **Location**
   after a repeated name. No bench unit currently has Location set, so this was
   only proven with synthetic data — setting Location on a couple of real units
   and rescanning is the best test of it.
8. **USB and Multiview as a restricted User.** Read-only state was verified;
   an actual live pair/unpair and Multiview Show/Switch from a User account
   were deliberately not performed, to avoid re-cabling a working bench.
9. **The restricted screen on a real phone.** Checked at 390 px in a headless
   browser; a real handset in one hand is the honest test.
10. **Anything that feels slower than V1.1.0.** Discovery measured 1.2 s for 10
   devices, unchanged — but trust your own sense of it.
