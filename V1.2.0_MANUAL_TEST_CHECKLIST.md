# OmniSuite V1.2.0 — Manual Test Checklist

Hands-on testing before release. Automated acceptance has already passed; this
is about how it *feels* on real equipment and real browsers.

**Candidate:** `OmniSuite-V1.2.0-Windows-x86_64.zip`
**Location:** the `release\` folder of the OmniSuite working copy
**Size:** 33,319,484 bytes (31.8 MB)
**SHA-256:** `ad4f2b8fa07183b1e5bdc3fee15fe2c6202dc39ce33d4325c9ab0fa3a54b750e`
**Built from commit:** `b13f5f5` on `feature/remote-user-routing`

> This build **supersedes** every earlier V1.2.0 candidate, including
> `ac42ac4d…`. On top of what those carried it fixes the route that worked
> while reporting *Route command failed*, gives every refusal a reason you can
> act on instead of a bare *not permitted*, adds **Unroute**, shows what each
> display is showing, remembers the display you chose, picks up a device
> change without the assignment being touched, and turns a direct access link
> into a control panel that stays on its own address.

> The directly runnable build is at `dist\windows\OmniSuite.exe` if you would
> rather not unzip anything.

## Worth paying attention to

These are the areas this release changed most, or where testing could only go
so far:

1. **Routing to a display that is showing a Multiview.** It now just
   happens — no question, from the A/V Matrix, the Multiview page's display
   drop, and both kinds of User. The Multiview is kept and can be shown again.
   If the route fails, the display goes back to its Multiview rather than
   sitting blank. **One source on your bench, `at-omni-111-04553`, still fails
   every route** — its session multicast is the unconfigured default
   `239.0.0.1`, and it fails identically from the Admin matrix, so that one is
   a device setup matter rather than anything in this build.
2. **Clear Units keeps devices that are assigned to a User.** With Remote
   Access on, it tells you how many it kept and for whom. To clear one, take it
   away from the account first — or use the button in Manage users ▸ Device
   names, which clears everything and names who is affected. With Remote Access
   off, Clear behaves exactly as it always has.
3. **Source pictures on the User screen.** Each card is the picture. One of
   your encoders has thumbnails switched off and its card says so — worth
   confirming that reads sensibly.
4. **Sign out.** New on the Admin screens; it was only ever on the User
   screen, which is why you had to clear cookies.
5. **Open the Remote Access URL in a fresh browser.** It should show the
   sign-in page. That is the defect you found: it was answering with
   `{"error":"authentication required"}` as plain text. Sign in as the
   administrator and you should land on the ordinary OmniSuite screens; sign in
   as a User and you get the restricted screen.
6. **The certificate now has to match the address.** Yours was made for
   `.185` while Remote Access is configured for the Wi-Fi adapter at `.180`,
   and the new build refuses to start HTTPS on an address the certificate does
   not name. Validating the remote flow meant fixing that, so **a certificate
   for `192.168.100.180` was created during testing** and Remote Access is on
   — fingerprint `DDCCA594DD56C320`. Your original `.185` pair is not deleted;
   it is kept in the session scratchpad if you want it back.

   To see the refusal for yourself: switch the Network to another adapter and
   turn Remote Access on. Settings should say the certificate is for a
   different address and offer **Create one for this network**.
7. **Direct access links.** New. Manage users → open a User → tick *Allow
   passwordless direct link*, copy it, and paste it into an incognito window.
   No password prompt, the restricted screen appears, and the token is gone
   from the address bar. Then **Regenerate** and confirm the old link fails.
8. **Switching between the two adapters.** Both should be listed —
   `Ethernet 3` and `Wi-Fi` — and either should be selectable. Your saved
   configuration currently names Wi-Fi, which is what you chose last time, and
   OmniSuite keeps it: it does not quietly move to the wired adapter because
   one exists. Switching between them should update the address, the link and
   the certificate status together.
9. **Remove certificate.** It deletes one OmniSuite created, or just
   stops using one you supplied, and refuses while Remote Access is on.
10. **The certificate warning.** The first visit from each browser will warn.
   Decide whether the wording in the User Guide matches what you actually see
   on Chrome/Edge/Safari.
11. **Duplicate friendly names.** OmniSuite adds the device's own **Location**
   after a repeated name. No bench unit currently has Location set, so this was
   only proven with synthetic data — setting Location on a couple of real units
   and rescanning is the best test of it.
12. **USB and Multiview as a restricted User.** Read-only state was verified;
   an actual live pair/unpair and Multiview Show/Switch from a User account
   were deliberately not performed, to avoid re-cabling a working bench.
13. **The restricted screen on a real phone.** Checked at 390 px in a headless
   browser; a real handset in one hand is the honest test.
14. **Anything that feels slower than V1.1.0.** Discovery measured 1.2 s for 10
   devices, unchanged — but trust your own sense of it.
