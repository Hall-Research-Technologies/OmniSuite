1. Before First Use

OmniSuite runs on the management PC and talks to each device directly. Nothing discovers devices on its behalf, so what that PC is allowed to reach is what OmniSuite can manage. Work through this list once, before the first scan.

  1. Connect the management PC to the appropriate network — the network the Omni devices are on, or one that routes to them.
  2. Select the correct network interface in OmniSuite. The adapter selector is on Device Info, beside the Targets field and the Scan button, and it is the only interface picker in the application. The choice is stored on the server and identified by the adapter's address rather than by its position in the list, so it survives a page refresh, navigating to another page and an OmniSuite restart. If the PC has more than one adapter — a dock, a wireless connection, a VPN — choose the one carrying the control network deliberately.
  3. Allow OmniSuite through the host firewall and any endpoint-security software when you are prompted. Because OmniSuite talks directly to devices, an operating-system firewall rule or an endpoint-security policy can block discovery and management even when the device is otherwise reachable on the network. A unit whose own web page opens in a browser can still be invisible to OmniSuite if the traffic OmniSuite uses is being filtered.

What OmniSuite puts on the network

This is what has to be permitted, described as behaviour rather than as a rule to paste in: the exact rule, and whether it is expressed inbound, outbound or per application, depends on the operating system and the security product in use.

PurposeTraffic
OmniStream encoder / decoder discovery, configuration, firmware and pollingHTTP / WebSocket from the management PC to each unit, on the port chosen in Settings › WS Port (80 (ws/http) or 443 (wss/https)). Each candidate address gets a short TCP reachability check first.
Finding unknown standalone HW-OMNI-311/324 USB extenders on the attached networkThe HW-OMNI-311/324 binary UDP API on port 6137, sent as a local broadcast, with the devices' replies returning to OmniSuite.

Using OmniSuite itselfThe browser connects to the local OmniSuite server; the address and port it bound to are printed at startup.
Do not disable your firewall. What OmniSuite needs is permission for its own process and the traffic above, not an unprotected machine. On a corporate PC, endpoint-security policy is often centrally managed and cannot be changed locally; in that case the permission has to be granted by your IT department, and the table above is what to give them.

What a scan can reach, and what it remembers

  • Local broadcast discovery does not cross a router. It finds unknown devices on the directly attached network only. That is how IP broadcast works, not a missing feature.
  • Routed USB discovery is directed, not broadcast. Extenders on another subnet are found by scanning the configured discovery networks — the Targets expression on Device Info writes through to the directed USB discovery ranges — and are kept visible afterwards by directed unicast polling of their known addresses, which does route.
  • Known devices are refreshed by subsequent scans. You never have to empty the list to update it: scanning again re-probes every device already known, including ones that have gone quiet.
  • A rescan reconciles by hardware identity. Devices are matched on MAC address, and information that has changed — address, hostname, firmware, status — is updated on the record that already exists.
  • A device that changes IP but keeps its MAC updates its existing inventory entry. It does not appear a second time, and the row it had at the old address does not linger.
  • Firewall or security policy can prevent discovery or management even when the device is otherwise reachable on the network. Treat it as a first suspect rather than a last one.
Clear Units is not a normal refresh mechanism. Do not use it to update stale information. To bring the list up to date, scan again. Clear Units empties the inventory — it is for deliberately starting over, and it also resets the topology advisory acknowledgements. See Scanning and Discovery.

2. Settings

Settings is the gear button in the page header. It is present on every page — Device Info, Configure, A/V Matrix and USB Matrix — in the same position, and it opens the same dialog with the same state everywhere. There is one implementation of the dialog, and it reads and writes the server (/api/config and /api/ui_preferences), so there is no page-local copy that could disagree with another page.

This is the first place to check before scanning or sending writes.

Choosing the firmware folder

A browser file input cannot return a directory path, and OmniSuite does not pretend otherwise. Choose Folder opens the application's own folder browser, which lists directories on the machine running the server. You can double-click through the tree, pick a drive, or type/paste a full path. The chosen path is stored server-side in config.json, so it survives a restart, and the firmware selector then lists the .vpup2 files in that folder.

TS Dump / support information

The dump is a single JSON file for support. It carries the current collected settings and status, with passwords masked, plus four derived sections:

SectionContents
usb_endpointsOne entry per USB endpoint: model, role, addresses, firmware and Icron revision, network mode and relation, liveness and where it came from, classification and parent identity, configured peers, and per-peer link state with its timestamps.
usb_routesEach configured USB relationship with both endpoints identified, the provider that owns it, current link state, and whether the control plane and the data plane were verified.

Fields whose value is unknown are deliberately left in the dump rather than stripped: "we do not know this" is usually the answer a support engineer needs. If one section fails to build, the rest of the dump is still produced and the failure is named.

OmniSuite itself tries port 8080 first. If that port is already taken it uses the next free port — 8081, 8082, and so on — and the address it actually bound to is printed at startup.

3. Appearance

The preset applies to every control. Buttons, tabs, toggles, the routing mode selector and the status messages all take their colour from the chosen preset, on all four pages, in both light and dark mode. A destructive action — Reboot Selected, Remove Selected — stays recognisably destructive under every preset: it is filled in the critical colour and carries a ring that no other button has, so it never comes to look like an ordinary primary button even in a palette whose accent and critical colours are close. Hovering shades a control, pressing it deepens it, and moving with the keyboard draws a focus ring; none of these change a control's size, so nothing on the page moves as you interact with it. A control you cannot use is dimmed and shows a "not allowed" cursor.
Buttons say how important they are. The action a page exists for — Scan on Device Info, Upgrade Selected, and the main button of each dialog — is filled with the preset’s accent colour. Everyday utilities such as Clear Units, Set NTP, Slate Manager and Inventory are quieter but still plainly clickable. Destructive actions are filled in the critical colour and carry a ring no other button has. This guide follows the same preset and light/dark setting as the rest of the application.
Selected controls are filled, not outlined. Wherever one choice out of several applies — the page tabs, the A/V Matrix AV / Video / Audio selector, the layout and preset choosers, and every on/off toggle — the active one is filled with the preset's selection colour while the others stay quiet. Every toggle can also be reached with the Tab key and operated with Space.

Appearance lives in the Settings dialog and is presentation only. It never touches discovered units, routes, scan settings, USB state, topology acknowledgements or any credential.

ControlValuesNotes

The four layouts

  • Classic — the familiar OmniSuite layout, stated as a choice rather than as the absence of one.
  • Compact — denser tables and quieter chrome, so more rows fit on screen.
  • Modern — grouped into cards with a visible hierarchy.
  • Workspace — a constrained, centred work area with a maximum width and slightly tighter spacing, so a wide display does not stretch every table across the whole viewport. The USB Matrix keeps the width it needs on its own page.

Your choice is remembered in the browser so the first frame is already correct, and on the server so it follows you to another browser and survives a restart.

Reset Appearance

Reset Appearance returns the layout, palette, light background and theme to their defaults (Classic, Default preset, dark). It is immediate and needs no confirmation because it is visual and reversible. It touches no credential, port, timeout, concurrency, firmware path, scan interface or target, USB discovery range, route, topology acknowledgement, cached device or device configuration.

Do not edit cache files while OmniSuite is running. To refresh device information, scan again; Clear Units is not a refresh. When you do want to start from an empty inventory, use Clear Units, and close OmniSuite before manually deleting any cache/config file.

5. Scanning and Discovery

Device Info owns discovery. Its adapter selector, Targets field, Scan button and Clear Units button drive every provider. No other page has a discovery console, an interface picker or a clear action; the other pages view and configure what discovery has already found.

  1. Choose the network adapter that is connected to the Omni control network.
  2. Leave Targets blank to use the adapter's detected range, or type a specific range such as 192.168.100.1-254, CIDR such as 192.168.100.0/24, or comma-separated IPs.
  3. Click Scan. Discovered units are cached and reused by Device Info, Configure, A/V Matrix, and USB Matrix.
  4. Use the X inside the Targets field to clear manual input and return to the selected adapter range.

The adapter choice and the Targets expression are both remembered. They are stored on the server and survive a page refresh, navigating to another page and back, and an OmniSuite restart. The adapter is identified by its address rather than by its position in the list, so a reordered or renamed adapter list cannot silently change what you chose; if the saved adapter no longer exists, OmniSuite says so and falls back to the normal default.

Targets is also the single definition of where to look for USB devices. Saving it writes through to the directed USB discovery ranges, so a routed subnet is entered once rather than in two places. A target expression that cannot be parsed as a range is reported back, and the rest of the preference still saves.

What Scan actually does

One click dispatches two independent providers. The OmniStream encoder/decoder scan returns on its own timing and is never made to wait for USB work; USB discovery runs in the background and its results, and the USB count, arrive afterwards.

The USB side dispatches all of the following, asynchronously:

  1. a directed re-probe of every known standalone endpoint, including ones currently offline — a device that stopped answering may simply have moved, and its recorded address is the only lead there is;
  2. parent-derived enumeration of every known USB-capable OmniStream unit;
  3. a local broadcast for unknown devices on the attached network;
  4. a directed range scan of the Targets expression / configured discovery networks.

Local broadcast versus directed discovery

MechanismWhat it is forScope
Local UDP broadcastFinding unknown endpointsThe directly attached layer 2 network only. Broadcast does not cross a router.
Directed unicastPolling and controlling known standalone endpointsAnywhere IP routing reaches, including other subnets.
Configured range scanFinding unknown endpoints at known addressesDirected, one candidate address at a time.
Parent enumerationDiscovering and refreshing integrated endpointsAnywhere the parent OmniStream unit is reachable.
There is no generic way to find an unknown device at an arbitrary routed address. If OmniSuite knows neither the device's address nor a network containing it, nothing can find it, because there is nothing to address. That is a property of IP, not a missing feature — OmniSuite does not sweep private address space. Entering the routed network in Targets is how you tell it where to look.

Range input is bounded before it is expanded, so an over-broad expression such as 10.0.0.0/8 is rejected immediately rather than being materialised. Range scanning is a discovery operation triggered by Scan; ordinary page polling never runs one.

On macOS and Linux builds, adapter discovery depends on OS interface data. If the adapter list looks wrong, use the Targets box to enter the intended subnet manually.

Clear Units

Scan results are merged into the existing list; rediscovering a device at a new address updates the existing row rather than adding a second one, because identity is the hardware MAC and not the IP address. Clear Units is the single reset:

  • clears the encoder/decoder cache, the scan results and the CSV export;
  • forgets the standalone USB inventory, so cleared devices do not reappear on a refresh;
  • resets the topology advisory acknowledgements.

It is inventory only. No packet is sent to any device, and no pairing, network setting or power state is touched. Configured USB discovery ranges are kept, and devices return after the next successful discovery.

Clear Units is not how you refresh stale data. A rescan already re-probes every known device and reconciles it by MAC, so a moved or changed device corrects itself without the inventory being emptied. Use Clear Units only when you deliberately want to start from nothing.

6. Device Info Page

The Device Info page is the fleet overview, the discovery console and the firmware workflow page.

Navigating the table

The leading columns are, in order, the selection checkbox, IP, Hostname, then MAC, so you read select, address, name, hardware identity. The first three — checkbox, IP and Hostname — are frozen: MAC and everything to the right of it scroll underneath them, so a row read at the far right of a wide table is still attributable to a device. The frozen widths are measured from what is actually rendered, so they stay correct in every layout and at any zoom.

The command area is locked in place. The page header, the scan bar (adapters, Targets, Scan, Clear Units) and the firmware bar (firmware selector, Upgrade Selected, the Encoders/Decoders/USB counts and the details toggle) stay on screen while the table scrolls beneath them. Only those compact command surfaces are pinned; the advisory banners scroll away with the rows, because a permanently pinned advisory costs the height you came for.

A mirrored horizontal scrollbar sits directly below the locked command area and above the table, so reaching it does not mean scrolling past every row first. It drives the same container the table's own scrollbar does, and the two stay in step whichever one you use. It is shown only when the table actually overflows its width, and disappears again as soon as it does not — for example after hiding the device detail columns. This is an application-wide rule rather than a Device Info feature: any section wide enough to need a horizontal scrollbar at the bottom also gets a synchronized one at the top — the Encoder, Decoder and USB tables on Configure, the LEX and REX inventories on the USB Matrix, and the route grids when they are wide enough. Each section scrolls independently: moving one does not move the others. A section that fits shows no top scrollbar at all.

Inventory Table

Shows the selection checkbox, IP, hostname, MAC, link speed, codec, timezone, NTP server, type, model, version, password state, status, blink, preview, USB role, and a Log button.

Use Show/Hide Device Details to hide or show TimeZone, NTP Server, Type, Model, Version, Password, and USB columns. Status, Blink, Preview and Log stay visible either way.

Unit Counts

The firmware bar shows Encoders, Decoders and USB counts. Encoder and decoder counts come from the OmniStream scan; the USB count counts each online USB endpoint once, by its hardware identity, so an endpoint inside an encoder or decoder is never counted twice.

Polling

Poll Units keeps status, version, hostname, timezone, NTP server, link speed, password state, and USB feedback fresh without another scan.

Open dropdowns and active edits are guarded so polling does not overwrite the field while you are working.

Codec

VCx is shown green. Other codec modes are shown red. If the discovered matrix has mixed codec modes, OmniSuite shows a mismatch warning.

Legacy units can change codec. Changing codec reboots the unit and requires confirmation.

LLDP and network topology

Each discovered unit is asked for its LLDP neighbour during the scan, so the inventory knows what each device is attached to. Nothing polls for it separately, and displaying it touches no device.

Hover a MAC address to open the LLDP panel: switch chassis, management IP, port ID, port description, age, TTL, and capabilities. A device that reports no LLDP simply contributes nothing — missing information is never treated as a second switch.

Multiple switches. When the discovered devices resolve to more than one switch chassis, traffic between them crosses an uplink, which is worth checking if performance problems appear. A banner says so, and the devices on the minority switch carry a subtle shade and a "Different switch" line on their MAC cell. Multiple switches are not presented as a fault. Where two groups are the same size, no group is designated as the odd one out.

Daisy chains. An OmniStream unit has a two-port bridge, so a device cabled behind another OmniStream unit reports that unit as its neighbour rather than a switch. OmniSuite follows the chain to the real upstream switch for grouping purposes, and separately keeps and shows the path: the row is marked "Daisy chained via" the unit in front, and the hover panel names both the unit in front and the upstream switch. A chain that cannot be resolved leaves the upstream switch honestly unknown rather than guessed. A daisy chain is a supported way to cable a system, not a fault, and it is not a second switch.

The daisy-chain advisory states a risk derived from topology, not a measurement. Downstream devices share the upstream link, so if several high-bandwidth streams run through it, that link is worth verifying. No device reports its stream bitrate to OmniSuite, so nothing here claims a link is congested, saturated or overloaded.

Dismissing an advisory. Each banner has a close control. The multi-switch advisory and the daisy-chain advisory are separate risks with separate acknowledgements, so dismissing one never silences the other. A dismissal lasts for the lifetime of the current discovered inventory:

OperationBrings the banner back?
Scan / Discover, however many timesNo
Scanning a different network, or changing TargetsNo
Discovering more devices, or a further switchNo
Background polling, or navigating between pagesNo
A device that becomes daisy chained for the first timeYes, once, for that new device
Clear UnitsYes — the acknowledgement belongs to the inventory and resets with it

Dismissing a banner silences the banner and nothing else. The minority-switch and daisy-chain row highlighting keeps describing whatever the current topology is, and follows it in both directions.

The USB column

Some OmniStream units have a USB extender built in. For those, this column shows which end of a USB link that unit is:

ShowsMeansIn practice

The column is deliberately just the role. Device Info's Type column tells you encoder or decoder, which is a different question — a unit can be a decoder and the USB device end at the same time — so the USB role is worth its own column. Everything else about the endpoint is on the tooltip.

Hover the cell and OmniSuite lists what it can actually vouch for about that endpoint:

Tooltip lineWhat it tells you

Paired is not the same as linked. “Paired peers: 2 (0 linked now)” means two routes are configured and neither is up at the moment — a powered-down peer, an unplugged cable, or a peer that lost its pairing table will all read that way. A configured route is a statement about configuration; it is not evidence that USB traffic is flowing. To act on USB routing, use Configure › USB or the USB Matrix, which show configured pairing and live link as separate columns.

Downloading a device log

Each OmniStream encoder and decoder can produce a diagnostic bundle for the manufacturer's support team. The Log button at the right-hand end of each row retrieves it.

  • Clicking Log first shows a short notice: “Device logs are encrypted and can only be decrypted and read by Engineering.” Choose OK to continue or Cancel to stop. Cancel is the highlighted, focused button, so pressing Enter by accident will not start a download; Escape and clicking outside the dialog also cancel. Nothing is requested from the device until you choose OK.
  • The notice appears every time. It is not something to dismiss permanently, because it is the reason not to expect to open the file yourself.
  • After OK, that device builds a fresh bundle and it downloads. The button shows … while this happens — usually a few seconds — and clicking again during that time does nothing, so one click is one request.
  • The file is saved as hostname_IP_timestamp.vdf, so logs from several devices never overwrite each other and each one says which unit and which moment it came from.
  • Nothing else in OmniSuite ever requests a log. It is not part of discovery, polling, startup, the TS Dump or the inventory workbook — only this button.
  • Retrieving a log does not change the device. Its configuration is untouched and it is not rebooted; the unit does work to build the bundle, so its fans may briefly spin up.
What is in the file. The bundle is encrypted by the manufacturer and is around 10 MB. OmniSuite passes the bytes through exactly as the device produced them — it does not and cannot read them, so it cannot tell you what is inside. Treat it as diagnostic material for Hall Research or Atlona support and send it only to them. Do not expect to open it yourself. OmniSuite never writes your device passwords into it.
If Log does not work. A unit that is powered down, on an unreachable network, or answering on neither the primary nor the fallback password will report that it did not return a debug log, and the button returns to normal. Nothing is left half-downloaded. Check that the unit's row shows a current status, that you can open its web page from the IP link, and that the Primary and Fallback passwords in Settings still match the unit — a log uses the same sign-in that discovery does.

Firmware Upgrade

  1. Select one or more units.
  2. Select the firmware file from the firmware selector. The list is the .vpup2 files in the folder set in Settings › Firmware Path; the refresh button re-reads that folder and the folder button opens it.
  3. Click Upgrade Selected and confirm the custom upgrade dialog.
  4. Rows move through queued/uploading/upgrading/rebooting/idle based on feedback and version polling.
Some units can time out during upload and need a reboot before retry. The app avoids leaving the UI stuck in an old state, but the device is still the source of truth. Watch for the version to update after the unit returns.

The inventory workbook

Inventory downloads an .xlsx workbook with two sheets:

  • Devices — the same columns the inventory CSV has always had, including HDCP settings, encoder Session 1/2 A/V multicast addresses, and decoder ip_input1/ip_input3 route values when collected. Parent OmniStream firmware belongs here.
  • USB — nine columns, in this order: Model, USB Role, Device IP, Hostname, USB IP, USB MAC, Firmware, Network Mode, Network. This is the operator's view of Configure › USB; peers, link state, status and diagnostics belong in the TS Dump instead.

Both sheets freeze the header row, carry an autofilter, and write addresses and MACs as text so Excel cannot reformat them. It is built from the same inventory the pages render, so one physical endpoint is one row. If the build does not include Excel support, the download falls back to the CSV.

9. Multiview

Multiview puts several sources on one display at once. You choose a decoder, choose a layout, drop a source into each window, and the decoder composites them into a single picture. It is built and recalled entirely from the Multiview page.

Multiview is video only. Sound still comes from one source — see Audio below.

Choosing a decoder

Everything starts with the decoder that will show the Multiview. Only decoders that answered and that support Multiview are offered. A decoder that is switched off or unreachable is not in the list at all.

A decoder that is reachable but cannot do Multiview right now is still listed, greyed out, with the reason — usually Video Wall or Fast Switching. Those are deliberate settings, so OmniSuite tells you rather than turning them off behind your back. Turn the conflicting feature off on the decoder and it becomes available.

OmniSuite remembers the decoder and the Multiview you were working on. Refresh the browser or go to another page and come back, and you are where you left off. If that decoder has since gone offline the selection is cleared rather than left looking valid.

Which sources can be used

The source list shows every encoder OmniSuite can use for Multiview, in one of three states:

StateWhat it meansWhat to do
ReadyUsable now.Drag it into a window.
Configuration requiredThe encoder is fine, but something on it still has to be set — usually its second session has no multicast address.Set it on the device. The tile says which field, and cannot be dragged until it is fixed.
Not eligibleOffline, or a model that cannot feed a Multiview window.Nothing. These are collected under encoder(s) not eligible with the reason, so a missing encoder is never a mystery.

Seeing what is on a source before you use it

Hover over a source tile and a preview of that encoder appears beside it, so you can tell two similarly named units apart without routing one to find out.

  • Preview disabled — the encoder is not generating a preview. Turn its thumbnail on from the Configure page if you want one.
  • Preview unavailable — the picture could not be fetched just now.
Preview is informational only. It never routes anything, never changes a source, and a source you cannot preview is still perfectly usable. OmniSuite never switches preview generation on by itself.

Choosing a decoder

When you pick a decoder that is already showing a Multiview, OmniSuite opens that Multiview for you: the canvas fills with the windows that are on screen and the sources actually feeding them, and the page shows it as live.

If the decoder is not showing one, the page waits for you to choose a saved Multiview or create one. What the decoder is doing always takes precedence over what you were last looking at.

Creating a Multiview

  1. Choose the decoder.
  2. Press + New Multiview.
  3. Choose a layout — 2x2, Side-by-Side, one of the four Picture-in-Picture positions, one of the four 1+3 arrangements, or 4-Split.
  4. Give it a name. The name follows the layout until you type your own.
  5. Drag a source onto each window, or click a source and then click a window.
  6. Press Save Multiview.

The Configuration panel below the canvas shows exactly what Save will do before you press it, and the confirmation lists every change.

Saving does not change the picture. It stores the layout on the decoder and leaves the display alone. Nothing appears on screen until you press Show on Display.

Creating something new, versus editing what is there

+ New Multiview starts a separate creation: the panel is headed Create New Multiview and the Multiview you were looking at is left exactly as it is. Cancel returns you to it unchanged.

When you are editing a saved Multiview the panel is headed Editing <name> and says whether it is Saved or has Unsaved changes.

When Save is available

Save Multiview is greyed out until something you can save has actually changed — the name, the layout, or which source is in which window. It says No changes to save so you are not left wondering.

Things that change on their own never enable it: a source going quiet, a window's health, a preview refreshing, or the engineering figures updating. Those are readings, not edits.

After a successful save it greys out again. If a save fails, what you typed is still there and Save is still available, so you can correct it and try again.

The Save confirmation

Saving lists what it will do and asks you to confirm, because it reconfigures encoders that other displays may be using. If you would rather not be asked, tick Do not ask again for this version.

That preference is remembered for this version of OmniSuite. When you upgrade, the confirmation appears once more, because a new release may do something different. You never have to clear it by hand, and turning it off here does not affect any other warning.

Several Multiviews on one decoder

A decoder holds as many saved Multiviews as you want, and exactly one of them is on the display. They are listed under On this decoder, and the one currently showing is marked. Pick any of them from the Multiview dropdown to open it.

Showing one on the display

Show on Display prepares every source the Multiview needs and then switches the display to it. It runs immediately — choosing a Multiview and pressing the button is the instruction, so there is no extra dialog.

Each change is read back from the device afterwards. If anything cannot be confirmed, the whole operation is undone and you are told what failed. A Multiview that is already showing and already correct can be shown again safely; nothing is rewritten.

Editing versus changing what is on screen

This is the distinction to hold on to, and the canvas states it in words:

The Multiview you have openWhat the canvas saysWhat a drop does
Not on the displayNot on the display — changes are saved, and shown when you chooseEdits the saved layout. Nothing on screen changes until you Save and Show.
On the displayLIVE — changes made on this canvas are applied immediately, with the canvas outlinedChanges the picture straight away.

Switching a window live

When the Multiview is on the display, drag a new source onto a window and it switches. There is no confirmation: the canvas already carries the LIVE banner, and a dialog on every drop would only train you to click through it.

Only the window you dropped on changes. The others keep their picture. The window shows Switching… while it happens and Live once the decoder has confirmed it.

A live change that succeeds becomes part of the saved Multiview, so recalling it later brings back what you last had on screen rather than what you originally saved. A change that fails is undone and the window goes back to the source it is still showing.

The × on a window clears it. On a live Multiview that takes effect immediately too.

What the windows show

Each populated window shows that source's live preview where one is available, with the source name, address and the decoder input carrying it laid over the top. A window whose source has no preview keeps the plain appearance and says so. The canvas always reflects what the decoder is actually receiving — if someone changes a window from the front panel, that is what you will see.

Audio

Multiview carries picture only, so the sound comes from the main window's source — the largest window in the layout, or the first window where all windows are the same size. It uses that source's normal audio stream and the decoder's existing audio input.

Change the main window and the sound follows it. Change any other window and the sound is left alone.

Bitrate

OmniSuite sets the Multiview stream bitrate for you, from the size of the window it feeds:

LayoutTarget per window
Side-by-Side200 Mb/s each
2x2200 Mb/s each
Picture-in-Picture300 Mb/s main, 150 Mb/s inset
1+3 (any position)300 Mb/s main, 150 Mb/s each small window
4-Split300 Mb/s main, 150 Mb/s each small window

Windows of the same size always get the same target.

What a source can actually deliver depends on what it is already doing. Each encoder has a 900 Mb/s budget shared between its primary stream and its Multiview stream, so the Multiview stream gets its target or whatever the primary stream leaves — whichever is smaller.

OmniSuite never reduces the primary stream to make room for Multiview. Every decoder watching that encoder normally would lose picture for a moment if it did. So a source whose primary stream is at 750 Mb/s gives its Multiview window 150 rather than 200, and the Configuration table shows both numbers — the bitrate it got, and the target it was aiming for. If you want the higher figure, lower the primary stream on the encoder yourself.

A source with almost nothing left is refused by name rather than being used badly.

Using one source in more than one window

The same source can fill two windows of the same size. It is encoded once and arrives once, so it costs no extra bandwidth.

The same source in two windows of different sizes is refused. An encoder produces one picture at one size, so it cannot feed a large window and a small one at the same time. OmniSuite tells you which two windows are in conflict; use a different source for one of them.

One source can fill at most two windows.

Copying a Multiview to another decoder

Several screens often need the same arrangement. Open the Multiview you want, press Copy to Decoder… and choose where it should go.

This copies the layout and the source in each window, and saves it on that decoder. It changes no picture: neither the decoder you copied from nor the one you copied to. Show it there when you are ready.

  • If that decoder already has a Multiview with the same name, OmniSuite asks rather than overwriting it, and offers to keep both.
  • If the target cannot run the Multiview — Video Wall is on, Fast Switching is on, or it is not a Multiview decoder — it says so and copies nothing.
  • If one of the sources is switched off at the moment, the copy still happens and keeps that window. You are told which source was not answering; it is set up when the Multiview is shown.

Decoder groups

A group is a set of decoders meant to show the same thing — the screens over a bar, a row of monitors, an overflow area. Press Groups… to create one, name it, and tick the decoders that belong to it. Groups are remembered by OmniSuite; they are still there tomorrow.

If you never need groups, you never have to make one. The page works exactly as it always has for a single decoder.

With a group selected you can:

ActionWhat it does
Save Multiview to groupSaves this Multiview on every decoder in the group. No picture changes.

When a group cannot show something

The encoders behind the windows are shared. An encoder sends one picture size at a time, so if one decoder in the group wants a source as a large window and another wants the same source as a small one, that cannot be done — by any product, not just this one.

OmniSuite works this out before it changes anything and refuses the whole operation, naming the source and the decoders that disagree about it. Give that source the same window size on every decoder in the group and it will go through. Nothing is written to any device by a refused group operation.

Changing a source across a whole group

After you show a Multiview on a group, a bar appears saying which group you are working in and how many decoders it covers. While that bar is showing, dragging a new source onto a window changes it on every decoder in the group, checked and applied together.

Press Leave group context and you are back to working on the one decoder. A single-decoder change never moves the rest of the group.

When a group falls out of step

Check group reports each decoder as:

OmniSuite does not quietly put a drifted decoder back, because it cannot know that you did not mean it. Use Show on group again when you want them back in step.

Showing on a group configures the decoders one after another and confirms each one. If one fails, the ones already changed are put back and you are told whether that succeeded. These are separate devices on a network, so this is a careful best effort rather than a guarantee that all of them change at the same instant.

Multiview and the A/V Matrix

A decoder that is currently showing a Multiview is marked MULTIVIEW on its row in the A/V Matrix, and no video crosspoint is shown for it — because the picture is a composition of several sources, not a route from one encoder. Hovering the row explains this.

Audio may still show a source on that row, and that is correct. Multiview sound comes from the main window's source over its ordinary audio path, so the matrix is telling you exactly where the sound is coming from.

You can still route a normal source to that decoder from the matrix. Doing so exits Multiview and shows the route you asked for. OmniSuite warns you first:

Multiview is active on this decoder. Completing this route will exit Multiview and replace the Multiview display with the selected A/V route.

The saved Multiview is not deleted. It stays in the Multiview dropdown and you can show it again whenever you like; it will be rebuilt against whatever the sources are doing at that time.

If that decoder belongs to a group, only that one decoder leaves Multiview — the rest of the group carries on. It is then reported as Drifted until you choose to show the group Multiview again.

The warning appears once per session — after you have acknowledged it, further routes that exit Multiview during the same session go straight through. Refreshing the page or moving between pages does not bring it back. Ticking Do not show this again stops it appearing in future sessions as well.

If the route cannot be completed, OmniSuite puts the Multiview back rather than leaving the display blank, and tells you so.

Deleting a Multiview

Delete Multiview removes it from the decoder. If it is the one on the display, OmniSuite moves the display elsewhere first and then releases the decoder inputs it was using.

Limits worth knowing

  • Multiview is 1920x1080. The display output is set to 1080p while a Multiview is shown. A Multiview saved at another resolution by an older release is listed but cannot be shown, and says so rather than failing when you press the button.
  • Video Wall must be off on the decoder.
  • Fast Switching must be off on the decoders that cannot combine it with Multiview.
  • A layout can use at most four different sources.

10. USB Endpoints and USB Matrix

The USB Matrix pairs LEX and REX endpoints. A LEX (local extender, USB host) is where the computer is; a REX (remote extender, USB device) is where the peripherals are. LEX endpoints are columns and REX endpoints are rows.

Standalone and integrated endpoints

OmniSuite handles two kinds of USB endpoint, and the distinction decides how each one is discovered, controlled and reported:

StandaloneIntegrated
What it isAn HW-OMNI-311 (host/LEX) or HW-OMNI-324 (device/REX) as its own unit.The USB/Icron endpoint inside an OmniStream E4521 (LEX) or D4511 (REX).
Discovered byUDP broadcast, a directed range scan, or a directed poll of its known address.Its parent OmniStream unit, which normal discovery already talks to.
Identity, model, hostnameThe unit's own.Supplied by the parent. A USB endpoint is matched to its parent by exact hardware identity, never by address proximity or hostname pattern.
IdentifyThe extender's own blink.The parent OmniStream unit's identify.
RebootThe extender's own reboot.The parent is rebooted instead.
Network configurationDHCP / static, from OmniSuite.Not offered from OmniSuite; it is managed on the parent unit.
Pairing shown fromA fresh read of the endpoint itself.The parent's USB configuration, which is the established control plane.

Until OmniSuite can prove which of the two an endpoint is, it says so and withholds device-specific commands rather than guessing. That resolves on its own as soon as the parent information arrives — no USB rescan is needed.

A standalone HW-OMNI-311/324 does not keep its pairing table across a power cycle. After one loses power its routes have to be re-established, and any peer that did keep its own table will disagree with it until they are.

Routing from the matrix

A cell states the relationship you want. OmniSuite reconciles the hardware to it; you do not perform the intermediate steps.

You doIt means
Click an empty cellRoute this REX to this LEX.
Click an active cellRemove this route.
Click another LEX's cell for a REX that already belongs to a LEXMove this REX to that LEX.

There is no step where you unpair the old route first, and no message telling you to. Moving a REX is one click: OmniSuite reads the authoritative state, releases only the conflicting relationship, establishes the requested one, and verifies both endpoints. Everything else on the old host is left exactly as it was.

Because a click states an end state rather than a command, OmniSuite also handles the states hardware is genuinely found in: already routed (nothing is sent), configured on one endpoint only (it converges, commanding only the endpoint that is missing the relationship), or owned by another host (it moves).

If a move cannot complete, the result distinguishes what actually happened — the endpoint could not be released and nothing was changed; or the new route failed and the previous one was restored and verified; or the new route failed and the restoration could not be confirmed. Failures surface in the ordinary toast.

A cell is drawn as pending while the transaction runs, and only shows a finished state once a fresh read of both endpoints agrees. A route is never painted from a click, an HTTP response or a device acknowledgement, so an intermediate state is never displayed as though it were your completed action.
  • Pairing feedback may take longer than the physical unit action because the UI waits for verified device state.
  • Auto-Refresh keeps the matrix current; adjust the interval for large systems. Extra open pages do not multiply device traffic — one shared backend refresh serves the Matrix, Configure and the Device Info count.
  • An intersection that cannot be routed is disabled and says why: the endpoint is offline, its ownership is not confirmed, its identity is unavailable, its pairing state is stale, or the two endpoints are not on the same USB subnet.
  • The LEX and REX detail tables list one row per physical endpoint. They expose USB type, host port and device filtering where the unit supports them; a standalone HW-OMNI-311/324 does not inherit those controls, and its unsupported fields read as fixed, not applicable, or not established rather than offering a selector that would do nothing.

A USB route never crosses a subnet

Management is routed; USB is not. OmniSuite can query, configure, identify and reboot an endpoint through a router perfectly well. A USB pairing between endpoints on different subnets does not work, and OmniSuite will not create one.

Compatibility is computed from the two endpoints' own addresses and subnet masks, with real address arithmetic — nothing assumes a /24, and the controller's own subnet is irrelevant. Both endpoints must resolve to the same network, and each must fall inside the other's.

For an integrated endpoint the judgement uses the Icron interface's own IP and mask, as the parent reports it — never the parent's management subnet. An E4521 managed on 192.168.100.x whose USB endpoint sits on 192.168.200.0/24 belongs, for pairing purposes, to 192.168.200.0/24.

The check fails closed, and it runs on the server immediately before anything is written:

What is knownResultWhat the cell says
Proven to share a subnetOfferedAvailable
Proven not toRefusedDifferent USB subnet
Not proven either wayRefusedUSB network information unavailable

Both disabled cases keep the addresses and masks they judged, for diagnosis. Routed endpoints stay on both axes; only their intersection closes, which is itself useful topology information. A reassignment checks before it releases, so a REX is never unpaired from a working host only to discover the destination was not allowed. Existing routes are never torn down because information went incomplete — only creation is refused.

One host, several peers

An HW-OMNI-311 can own several REX peers at once, so the matrix does not restrict a 311 to a single peer. A REX has a single owner, so each REX row is single-select — which is exactly why clicking another LEX for an owned REX is a move.

Adding or removing one peer affects only that peer: a host holding several keeps the rest untouched, and that is true whether the peers are standalone or integrated.

Link state is summarised from every peer, never from one value standing in for all of them. A host with five peers all linked reads Linked / 5 peers; some linked reads Partial — 3/5 linked; the per-peer detail is on the tooltip.

What was physically tested

One HW-OMNI-311 was validated on hardware holding five REX peers simultaneously — two standalone HW-OMNI-324 and three integrated D4511 — added one at a time through the production Matrix endpoints and verified from both sides after every addition. Each REX independently named the host, no addition displaced an earlier peer, removing one route removed exactly that peer, and an application restart reconstructed the whole five-peer state from the hardware.

Five is the number that was tested, not a discovered maximum. The documented model for an HW-OMNI-311 host is seven peers; five is simply how many have been proven to carry USB simultaneously. The integrated E4521's capacity is a separate question and is measured separately: one E4521 was observed holding two peers at once, and no E4521 capacity beyond two is claimed. Capacity for peers is also not a statement about how many USB peripherals can be used.

Route combinations, and how far each one has actually been proven:

CombinationControl plane (pair / unpair)USB data plane
E4521 → D4511The established path, unchanged.Verified (pre-existing).
HW-OMNI-311 → HW-OMNI-324Verified through the production endpoints.Verified — peripherals were physically run across the five-peer topology.
HW-OMNI-311 → D4511Verified through the production endpoints.Verified — same physical test, which carried both families at once.
E4521 → HW-OMNI-324Verified through the production endpoints: pair and unpair were each acknowledged on both endpoints and both peer tables agreed.Not verified. No peripheral test has been performed for this combination.

The mixed combinations are labelled in the matrix as a mixed USB route whose data transport is not yet validated, and they are routable precisely so that test can be carried out. A successful pair is never treated as evidence that USB traffic crosses the link, and nothing about the other three combinations upgrades the claim made about E4521 → HW-OMNI-324.

USB firmware

An OmniStream unit and the USB module inside it are versioned separately, so the Firmware shown on a USB row is the firmware of the USB endpoint itself:

  • For a standalone HW-OMNI-311/324, it is that unit's own firmware, read from the unit.
  • For an integrated endpoint, it is the Icron endpoint's firmware, read from that endpoint. It is never the parent OmniStream unit's firmware. On the bench an E4521 and a D4511 both running OmniStream 2.1.2 carried Icron 2.0.9, and one D4511 carried an older Icron revision than its siblings — real per-endpoint variation the parent's firmware would have hidden.

Some units report no Icron revision. When that read has never succeeded, the Firmware field is left blank rather than being filled in from the parent, because that would state a version the module does not have. The workbook writes N/A for it.

The parent OmniStream firmware is still reported, on the Devices sheet of the workbook and in the Device Info inventory, where it belongs.

11. Configuration Popups

Session Popup

Opened from an encoder's Session link on the Configure page. It displays a unit selector at the top so you can move between available encoders without closing the popup.

  • Limited to Session 1 and Session 2.
  • Encoder, DSCP, Downmixing, Source, and Interface are dropdowns.
  • SAP Announce, Scrambling, Video, Audio, FEC, and AUX settings are saved from the popup.
  • Close returns to Configure without applying unsaved changes.

Encoding Popup

Opened from an encoder's Encoding link on the Configure page. It also includes an encoder selector at the top.

  • Shows encoder input, max bit rate, max bit depth, max subsampling, Force YUV, slate mode, slate logo, scaler, and thumbnail controls as supported.
  • Slate modes are off, auto, and manual.
  • Scaler resolution lists are dynamic per encoder. Encoder 1 and Encoder 2 may have different resolution options.
  • If Slate Logo is Not used, slate mode cannot be enabled.

Video Wall Popup

Opened from a decoder's Video Wall Configure button. The popup has a decoder selector so you can navigate between available decoder units while it stays open.

  • Polling is suspended for the edited video wall values while the popup is open.
  • Values are sent only when Save is clicked.
  • After Save, OmniSuite refreshes the selected decoder to verify feedback.
  • In pixels mode, display width and display height are hidden because they are not used.
  • Pixels mode offers incoming source resolution choices: 4K and 1080p. Width and height are populated read-only from that source choice, and the Video Wall Layout control calculates horizontal and vertical coordinates up to 5x5.
  • In inches or millimeters mode, do not apply the pixel math. Width, height, total display width, and total display height are handled as device measurement fields.

USB Network and Reboot Dialogs

Opened from the Actions column of Configure › USB, for a standalone extender.

  • The network dialog offers three explicit choices — DHCP, Static, and Cancel — so Cancel means cancel.
  • DHCP confirms with the device identified by model, address and MAC, and warns that the address may change. Identity stays the hardware MAC, so a new address updates the existing row.
  • Static opens a form for IP, mask and gateway, prepopulated where authoritative values exist, and validated for address syntax, a contiguous mask, and a gateway inside the same subnet before anything is sent.
  • Cancel, the close button, the backdrop and Escape all abort without transmitting.
  • An integrated endpoint never opens this dialog. It shows an explanation instead: its network is managed by the parent OmniStream unit.

Slate Manager

Opened from the Device Info footer. It uploads slate images and applies slate settings to selected units, all encoders, or all decoders.

  • Only .jpg, .jpeg, and .png images are accepted.
  • Images are validated before upload. Use 720 or 1080 resolution assets.
  • A small thumbnail previews the proposed upload before it is sent.
  • Slate delete removes selected slate files from target units when supported by the unit API.

13. Troubleshooting

Most reports of a missing or unresponsive device are answered by the same short sequence. The order matters: there is nothing to gain from rescanning a subnet the PC is not on, and nothing to learn from suspecting OmniSuite while its traffic is being filtered.

Device missing → Verify interface/subnet → Verify IP connectivity → Verify firewall/security policy → For routed USB: verify Discovery Network / known address → Scan again → Review TS Dump

The order to work through

  1. Device missing. State it precisely: which device, at which address, expected on which network. A device that has never been seen and a device that stopped being seen are different problems.
  2. Verify the interface and subnet. Check that the adapter selected on Device Info is the one connected to the device's network, and that the Targets expression covers the addresses you expect. A dock, a wireless connection or a VPN can quietly own the route you assumed.
  3. Verify IP connectivity. From the management PC, confirm the device answers at all — ping its address, or open its own web page. If it does not answer here, the problem is in the network or the device, not in OmniSuite.
  4. Verify firewall and security policy. Confirm that OmniSuite is permitted by the host firewall and by any endpoint-security product, for the traffic listed in What OmniSuite puts on the network. A blocked process and an empty network look identical from the UI. Do not disable the firewall to test this; permit OmniSuite, and involve IT where the policy is centrally managed.
  5. For routed USB: verify the discovery network or the known address. Broadcast does not cross a router, so a routed standalone HW-OMNI-311/324 is found only if its network is entered in Targets — which writes through to the configured USB discovery networks — or if OmniSuite already knows its address and can poll it by directed unicast.
  6. Scan again. This is the refresh. A rescan re-probes known devices, reconciles them by MAC and updates whatever has changed. Encoder and decoder results return first; USB discovery runs in the background and its results, and the USB count, arrive afterwards.
  7. Review the TS Dump. Settings › TS Dump downloads a timestamped JSON file built entirely from state OmniSuite already holds, so producing it sends nothing to any device. It carries per-endpoint discovery and freshness timestamps, liveness and its source, classification and parent identity, configured peers and link state, and the scan interface and directed ranges — including the fields whose value is unknown, which is frequently the answer. Attach it when you raise the issue.

Devices not appearing

  1. Firewall and endpoint security. Confirm OmniSuite is allowed to send and receive the traffic in the table above. This is the first check, not the last one.
  2. Adapter and Targets. Is the selected adapter on the device's network? Does Targets cover the right addresses? Leave Targets blank to use the adapter's detected range.
  3. Settings › WS Port. OmniStream units are identified through their API. Use 80 (ws/http) for normal units; 443 (wss/https) only when the unit's secure path is working.
  4. Credentials. A unit answering at its address still has to be readable. If Settings holds the wrong username or password, and the fallback password does not match either, a reachable unit may not be reported.
  5. Timeout. Too low a per-request timeout can make a reachable but slow unit look like it failed. Raise it on slow networks.
  6. An unknown device at an unknown routed address cannot be found. If OmniSuite knows neither the address nor a network containing it, there is nothing to address. Enter the routed network in Targets.

Devices appear but do not respond

  1. Firewall and endpoint security. A policy that permits some traffic and filters the rest will leave a device listed from an earlier scan while every action against it fails. Check this before changing anything else.
  2. Credentials. Check the password state on the Device Info row. Sync all Passwords moves units onto the chosen primary or fallback password where the current one is known.
  3. Timeout and concurrency. Raising Timeout, or lowering Concurrency on a busy network, often settles units that respond unevenly rather than not at all.
  4. Confirm it is still there. Read Status and how long ago the device was seen, then scan again to re-probe it at its recorded address. A device that moved is reconciled onto its existing row by MAC.
  5. A device that does not answer is an upstream condition. OmniSuite reports it as such rather than as an application error; a unit that is offline, rebooting or degraded is not an OmniSuite fault. Verify the unit itself before treating it as a software problem.

Routed devices not discovered

  1. Firewall and security policy, on the PC and between the subnets. Routed discovery and management are directed unicast; if that traffic cannot leave the management PC or return to it, a perfectly healthy routed device is simply never heard from.
  2. Broadcast was never going to find it. Local broadcast reaches the attached network only. A routed device missing from a broadcast-only scan is the expected result, not a fault.
  3. Is the network configured? Enter the routed network in Targets on Device Info. It is saved, and it writes through to the directed USB discovery networks used by Configure › USB, so it is entered once rather than in two places.
  4. Check the expression itself. An over-broad range such as 10.0.0.0/8 is rejected before it is expanded, and a target expression that cannot be parsed is reported back. A network with no IP path costs a bounded scan and yields nothing — which is the correct outcome, not an error.
  5. Give the background work time. USB discovery is never made to block the encoder/decoder scan, so USB rows and the USB count appear after it, on their own schedule.
  6. Routed management is not routed USB pairing. A routed endpoint can be discovered, polled and configured perfectly well and still be refused a route, because a USB pairing never crosses a subnet. That refusal is a separate matter from discovery.

USB devices show stale or unknown information

  1. Firewall and endpoint security. The directed UDP polling that keeps a USB row current is the same traffic as discovery. If it is being filtered, values age out and read as unknown while the endpoint itself is healthy.
  2. Scan again. A rescan re-probes known endpoints, re-enumerates parents and reconciles everything by canonical USB MAC. This is the refresh.
  3. Read the vocabulary literally. Unknown means the value was not read, which is not the same as "not linked"; a pairing figure past its age is stated as aged rather than presented as current; and after an OmniSuite restart a known standalone endpoint reads Offline (stale) until the next discovery reaches it.
  4. An integrated endpoint follows its parent. Its identity, liveness and pairing come from the parent OmniStream unit, so a parent that has become unreachable is what is actually stale. Check the parent on Device Info.
  5. An endpoint whose ownership is not yet proven says so. It resolves on its own once the parent information arrives, with no USB rescan needed.
  6. A standalone extender that lost power lost its pairing table. Its peers are gone and any surviving peer will disagree with it until the routes are re-established from the matrix. That is the device's behaviour, not stale display.
  7. A blank USB Firmware is deliberate. It means that endpoint has never reported one; it is never filled in from the parent's firmware.
Nothing in this section asks you to clear the inventory. Clear Units is not the fix for stale data — scanning again is, and it keeps everything OmniSuite has already learned. Clear Units is for deliberately starting from an empty inventory.
